The core idea

Map music by how it sounds, not how it's labeled

Anther places any song, playlist, album, or artist onto a fixed map learned from audio alone. Nearness on the map means acoustic similarity — never a genre tag.

  • Genre is display-only. It never touches the embedding, the index, the clustering, or the evaluation of the map itself.
  • A frozen reference corpus is the coordinate system. New songs are placed onto it, not re-clustered against each other.
  • Two audio front-ends (fast CPU features, and a neural embedding) feed one shared clustering + similarity API.

The guiding invariant: the quality of the map is judged by a genre-free evaluation harness — a track's own alternate mixes/versions should rank as its nearest neighbors.

Two-phase architecture

Same clustering & similarity API — only the input embedding differs

PHASE 1

Pre-computed librosa features

Fast, CPU-only. A 518-dimensional vector per track (chroma, MFCC, spectral shape, tonnetz, ZCR — 7 statistics each) matching the FMA dataset's exact schema.

PHASE 2

MERT neural embeddings

A 1024-dim vector from a 24-layer self-supervised music transformer (m-a-p/MERT-v1-330M). GPU-friendly, captures far more musical nuance.

Both phases produce vectors that flow into the same Leiden clustering and cosine similarity index — the pipeline downstream is identical, which makes the two directly comparable under one evaluation harness.

Phase 1 — engineered audio features

The science, and the bug that made it necessary

What's extracted: librosa descriptors — chroma (pitch class), MFCCs (timbre), spectral bandwidth/centroid/contrast/rolloff, tonnetz (tonal centroid), zero-crossing rate — summarized by kurtosis, max, mean, median, min, skew, std. 518 dims total.

Two correctness fixes that define this layer

  • Standardize before cosine. Raw feature families span a ~8,000× magnitude range (rolloff in Hz ≈ 10³ vs. chroma ≈ 10⁻¹). Row-L2 + cosine alone collapses to "nearest spectral rolloff." Columns are z-scored on corpus statistics first.
  • Explicit feature ordering. Features are a labeled MultiIndex, always align_to_corpus()'d before comparison — a silent same-length reorder is what made early uploads meaningless.

Loaded at native sample rate over the full track, matching FMA's official recipe so query and corpus features are computed identically.

Phase 2 — MERT embeddings

A self-supervised music transformer as the front-end

MERT is a 24-layer transformer trained self-supervised on raw audio. Anther uses the frozen 330M model and extracts a single 1024-dim vector per track with three deliberate design choices:

  • All-layer aggregation. Different transformer layers encode different musical facets — so each layer is mean-pooled over time, then averaged across all 25 hidden states (layer count read at runtime, so a model swap can't break it).
  • Multi-window. Several evenly-spaced fixed-length windows are embedded and pooled, so the vector represents the whole track, not just its intro.
  • Loudness normalization. Optional EBU R128 normalization removes the mastering-loudness production confound — described in the code as "the music-similarity analogue of a single-cell batch effect."

Every setting is captured in a self-describing embedding_config stamped into the index, so a query and corpus can never be silently compared under different settings.

Clustering — Leiden on the embedding

Borrowed wholesale from the single-cell RNA-seq playbook

Clusters are found by building a k-NN graph directly in the embedding / PCA space and partitioning it with the Leiden community-detection algorithm (Traag 2019; the SCANPY recipe).

Why Leiden

  • Every node gets a community — no noise bucket, no giant catch-all cluster.
  • One interpretable knob: resolution (low → broad, high → fine).
  • A single cosine metric throughout — eliminating an earlier cosine→euclidean mismatch.

The invariant

  • Cluster the embedding, never the 2D UMAP. UMAP/t-SNE distort density and distance; clustering them fuses or splits groups that aren't really there.
  • 2D UMAP is kept strictly for the picture.

A new song joins by k-NN vote against the labeled corpus in the same scaled PCA space — placement, not re-clustering.

Similarity search & calibration

Exact cosine, plus turning raw cosine into a human score

SongIndex is an in-memory exact cosine search (numpy dot product — correctness, not scale, is the concern under ~10k tracks). It self-describes its transform so incompatible indices can't be mixed.

The calibration problem

Raw MERT cosines sit in a narrow cone — random corpus pairs land at ≈0.95–0.98 — so a raw number is meaningless to a user and forces the edge-drawing threshold up near 0.98 with almost no headroom. Anther anchors a one-time 200k-random-pair cosine draw over the corpus to map raw cosine → a 0–100 score and a 4-tier band, so that:

  • the score on a map edge and the mentor's spoken "close" / "related" always agree;
  • the mapping is deterministic (seed=0) and reproducible by either process independently.

MERIT — disentangling melody, rhythm & timbre

The largest research upgrade: one similarity number → three perceptual axes

MERIT (Herremans et al., arXiv:2605.27346) keeps the same frozen MERT backbone and adds three tiny projection heads — melody, rhythm, timbre — each mapping a 5120-d backbone vector (layers {3,4,5,6,23}) to a 128-d unit vector. No backbone retraining; both representations come from one shared forward pass.

Why MERIT is a real improvement

Not a re-scaling — a genuinely better-shaped similarity space

The aggregate index is the 384-d concatenation of the three unit vectors. Because each sub-vector is unit-norm, cosine of the concat = the equal-weight mean of the three per-factor cosines — no separate weighting code needed at query time.

The frozen reference corpus

A stable coordinate system, not a re-clustered query set

Instead of re-clustering every new batch of songs, Anther builds a corpus once and freezes it: embeddings + Leiden clusters + fitted index + config, serialized as an immutable bundle with an integrity check.

  • Primary bundle: a frozen 100k-track corpus sampled from the Million Playlist Dataset (MPD — ~13.3M tracks, never embedded whole; deterministically artist-capped sampled).
  • Placement embeds a query with the corpus's own config, finds its cluster by k-NN vote, and returns nearest neighbors + tags — all against fixed coordinates.
  • Playlists and albums are placed asynchronously by a single-GPU background worker, with a configurable import cap and a graceful stop.

Because the corpus is frozen, the same song always lands in the same place — the map is a stable reference, not a shifting snapshot.

Two display layers on top of the frozen map

Read-outs that never feed back — "two scoreboards, one wall"

MICRO-GENRE TAGS

Two-stage weak supervision

  • Stage A: match each track's own playlist names against the everynoise 2000-genre vocabulary → noisy but in-distribution seed labels.
  • Stage B: a frozen multi-label probe trains on confident seeds, predicts for all tracks, then k-NN-propagates in MERT space to fill and denoise.
ARTIST ENRICHMENT

Provenance-carrying profiles

  • Image + followers from Deezer; origin, genres, labels from MusicBrainz.
  • Keyed by normalized name so it survives a corpus rebuild.
  • Identity resolution requires fuzzy match plus corroboration — ambiguous cases go to a review queue, never a guess.

Both are joined at API-read time and are strictly display-only — genre's sole carve-out, walled off from every metric that tunes the map.

The Mentor — an LLM at the ends only

Deterministic tools in the middle, no hallucination surface

A conversational "music mentor" reads the on-screen map with Anther's own similarity engine. Its architecture deliberately confines the language model to the two pipeline ends:

  1. Interpret — classify intent (advice / graph / off-topic) in one call.
  2. (everything in the middle is deterministic tool logic — seven read-only graph tools: resolve, sounds-like, compare, bridge, crossover, artist-tracks, tagmates)
  3. Narrate — rephrase the deterministic observations in the mentor's voice.
  • Session-aware graph context lets follow-up questions use the current map state.
  • Read-only: the mentor can never mutate the map — all edits go through UI controls.
  • Runs on one ~16 GB consumer GPU (Qwen2.5-7B + LoRA + RAG; serving peaks ≈2.6 GB).

The silent-correctness invariants

The rules that keep results meaningful

These are enforced across the codebase because breaking them makes results silently wrong rather than throwing an error:

1Never genre in embedding, index, clustering, or map evaluation — display only.
2Cluster the embedding, never the UMAP coordinates.
3Standardize before cosine (Phase 1) — corpus stats only.
4Query = corpus transform. Same config, checked by assert_compatible.
5Feature ordering is explicit, never positional — always align_to_corpus.
6Sample rates are phase-specific — native for Phase 1, 24 kHz for Phase 2.

Where it stands — open questions

Honest research state

  • All-layer vs. single-layer MERT. The richer all-layer embedding lowered top-1 self-retrieval on the tiny 107-track personal corpus (0.875 → 0.625) while holding recall@10 — a genuine keep-or-revert decision awaiting a larger labeled evaluation.
  • Micro-genre validation is complete on the corpus side (seed / fit / predict) but held-out FMA evaluation is blocked on a pending dataset download.
  • Phase-2 standardization (z-score before cosine on MERT) is still an open A/B.
  • MERIT is the current driver for edges, search, and ranking — validated on a real 8,000-track corpus sample, with the clustering still anchored to the MERT-1024 space.

Every design choice above is settled the same way: run the genre-free eval harness before and after, and keep the change only if the numbers improve.
